# 派发与唤醒

## 成员的派发：名册、@ 与事件（R5 / R4）

团队运行时只给「状态 + 工具」，不给「谁该知道什么」和「谁该动起来」。这一节是插件补上的三件事，
全部落在 `plugins/dsh-agent-team-roles`，不动 dsh 本体。

### 成员名册：只有 Lead 知道全部成员（§5.43）

teammate 的初始 prompt 里本来就点了 Lead 的名（`…\dsh-experimental-tool-agent-team\lib\index.js:276-284`），
但**反过来的名单 dsh 不提供**：谁在场、现在叫什么、什么状态，只有运行时知道。所以插件在
**Lead 自己的 agent scope** 上注册一段动态上下文（`lib/team-roster.js`）：

```js
agent.ctx.systemPrompt.context({ name: 'agent-team-roles:roster', order: 130, text: read })
```

- `text` 是**函数**，每次装配重新求值；文本没变就不会重复追加（`…\dsh-system-prompt\lib\types\index.d.ts:71-79`）。
- 内容是一段 `<team-roster>`：Lead 的身份、每个 teammate 的「名字（状态，模型）」、
  一句路由规则（**用户消息以 `@成员名` 开头时，把 `@成员名` 之后的原文原样 `send_message` 转给该成员**），
  以及「成员之间看不到彼此，只有你知道全部成员」。
- **空名册不贡献任何文本**（一个成员都还没起的时候，每轮塞一段「没有成员」只是噪音）。
- `description` 只作为上下文显示（§5.46 之后绑定不再读它），而且名字已经出现时不再重复显示。
- `{{` 会被写成 `{ {`：整段上下文在进模型前要过 `interpolate()`，一个解析不了的 `{{名字}}`
  **会抛错**（`…\dsh-system-prompt\lib\index.js:153-177`），而 `description` 是 `spawn_teammate` 的自由文本，
  真有人把成员描述成 `{{cwd}}` 的话，Lead 的整个 turn 会在装配时炸掉。拆开大括号既不影响阅读，也让语法安静。
- 名字与状态都来自 `agentTeams.listMembers(agent)`，读失败**只记一条 warning、不贡献文本**（宁可少一段，
  不能让 Lead 的 turn 装配失败）。
- **§5.65 两份通信骨架**（用户 m01743，m01746 批准）：名册末尾多一段 `LEAD_DISPATCH_LINES`
  （`## <任务标题>` / `**任务**` / `**待办**` + `- [ ]` / `**说明**`），成员那一侧原来是 §5.64 的一句
  「输出对话一律用标准 markdown。」，换成同构的 `TEAMMATE_REPLY_LINES`（`## <标题>` / `**结论**` /
  `**待办**`（`- [x]` 已做） / `**说明**`）。**只是给模型照抄的形状**：让 Lead 照写、成员照回，
  群聊里天然就是规范的 md，不额外加校验、不写进任何角色的 `AGENTS.md`。

### 成员确定性拿到角色（§5.46 / R1）

角色绑定以前靠**描述文本**命中，而 `spawn_teammate` 传给子会话的 `label` 是自由填写的 `description`
（`…\dsh-experimental-agent-team\lib\index.js:576` 传的是 description，**不是**成员名），所以只要描述不等于角色名，
绑定必然 miss，而且 miss 时连一条 warning 都不会有。

现在改成读**运行时自己校验过的成员名**：

- `agent/created` 里先取 `ctx.get('agentTeams').tryMembership(agent).name`（`lib/host/config.js:225` 的 `memberNameOf`），
  再用 `roleForMemberName(store.roles, name, prefix)`（`lib/roles.js`）找角色；**命中不了才退回描述匹配**，
  这样普通 `subagent`（没有团队名）仍然按老办法绑定。
- 时序是稳的：`team/member` 事件先 append+flush，子会话才开始（`…\dsh-experimental-agent-team\lib/index.js:561-570`）；
  名字由运行时校验（小写 kebab、队内唯一、不能叫 `lead`，`:342`），`provisioning` 阶段就能读到（`:397-410`）。
- 成员名 = **preset id 去掉前缀**（`memberNameForRole`）。中文角色名不会退化成空串：`slugify` 对没有 ASCII 的名字
  会落到一个稳定哈希（`lib/roles.js:195-210`），所以「架构师」的成员名就是 `r1abc` 这样的短键，
  名称与 slug 键天然分离。
- Lead 必须知道这个名字 ⇒ 名册那段上下文现在**额外带一段 `<team-roles>`**：每个可用角色一行
  `- 「架构师」 → name 用 "r1abc"`，外加一句「`spawn_teammate` 的 `name` 必须用这个，成员才会拿到该角色的 preset」。
  一个角色都没有时不贡献这段；**有角色但还没有成员时这段仍然贡献**（否则 Lead 无从知道该起谁）。
- 用 `ctx.get` 而不是第二次 `inject`：本模块已经持有 `agentPresets` 作用域，而**没装 Agent Teams 的 profile 仍要能开角色面板**
  （`inject(['agentTeams'])` 会让整块挂起）。读不到服务时静默返回 `undefined`，不影响其它功能。

### `@成员` 直接派发（§5.45 / R5）

主会话输入框里打 `@`，候选里就会多出**团队成员**一项（客户端侧用 `ctx.inputTriggers.registerSource`
注册了一个 `trigger: '@'`、`name: 'agent-team-member'`、`order: -10` 的源；名册优先读会话投影
`values.agentTeam.members`，读不到就回落到群聊 tab 那套事件窗口）。

这个构建里 `@` 草稿**永远不会走 `matchEnter`**（只有 `/` 开头的行会被送进 adjudication，
`…\dsh-client-ui-conversation\lib\client.js:3899-3923`），所以认领走**空格**：

1. `@成员名` 后面敲**空格** → `matchSpace` 返回 `{ claim }`，这一行进入「已认领」状态（`token` 自带尾随空格）；
2. 继续写正文 → 回车提交，正文（`@成员名` 之后的全部原文）作为参数交给我们；
3. 我们 `POST /command { action: 'team-send', sessionId, target, body }`，
   宿主侧 `agents.get(sessionId)` 拿到 Lead 的 live agent，再用 `agentTeams.sendMessage` 投给成员。

所以**草稿既不会进模型、也不会进 Lead 的会话**——这正是「@ 是派发，不是聊天」的意思。
`onPick`（从候选列表里点一个）返回同一种 `{ claim }`。

- 目标不是成员时返回 `undefined`，把 token **交还默认 sink**：`@文件` / `@会话` 这些引用照旧。
- 失败有明确文案：正文为空（`正文是空的，没有发送。`）、缺 `sessionId`、缺成员名、
  这个部署没有 Agent Teams 运行时、会话不在线（`这个会话不在线，没法把消息交给成员`）。
- 运行时**自己**拒了（成员刚好被 dispose、`TEAM_MAILBOX_FULL`、团队正在拆）时，错误会被包一层，
  把成员名放前面、原文照留：`没能把消息交给「架构师」：teammate "架构师" is not an active member` ——
  英文原因由运行时给，成员名是运维从原文里还原不出来的那部分。
- 群聊 tab **仍然是纯只读视图**，没有输入框——派发入口在主会话的输入框。

### 群聊 tab 的窗口边界（§5.48）

`conversation.view` 拿到的**不是整份会话日志，而是一段有界的尾部**——live 实测（本插件开发用的那个
session，28.9k 条记录）：窗口 1041 条、`seq 27883–28923`、`hasMore: true`；而这个会话的 8 条
`team/*` 记录在 `seq 21801–21862`。于是 `foldTeamEvents` 无米下锅，tab 渲染成
「本会话还没有群聊记录」+「运行时默认关闭，去 设置→插件 打开」——**对一个已经开着运行时、几十分钟前
刚收发过消息的会话这么说，是错的**（用户 m13214 报的就是这个）。

三处都改了（纯客户端侧，刷新页面即生效，不用重启 dsh）：

- 空态不再断言「没有」：窗口被截断时（`canPage && folded.hasMore`）说的是
  「这个窗口里没有群聊记录。」，并按 `scan.rounds` 报「已经往前翻了 N 段」；
- 给了**往前翻**的门：`props.loadOlder` 就是 `session.loadOlder`（`inject` 里本来就接好了），
  新挂载且什么都没看到时**自动往前翻 8 段**，翻完还空就给一颗「往前翻日志找找（再翻 8 段）」；
- 运行时提示改成**条件句**（「如果它还没开，去 设置→插件 里打开」），不再是「默认关闭，需要打开」。

真机复验：切到那个会话的「群聊」tab，自动翻页后渲染出 `成员 1 | 消息 4 | （历史未载完）`，
消息流里是 `lead → accept-probe PING-1：…`、`accept-probe → lead PONG-1`、`lead → accept-probe PING-2`
（都带 `已送达` 与时间戳），角色依赖图里 `@2` 周期两个下拉框各有两次 @。
截图 `Test\gui-team-chat-live-after-paging.png`（249976 B）。

### 群聊历史：宿主侧的日志投影（§5.50，用户 m13923 第 3 条）

§5.48 治的是「窗口里看不到」，但它治不了根：**浏览器那一侧永远只有一段有界的尾巴**。用户的
原话把方案定死了——「要么做一个独立的日志投影事件累计事件，要么直接从 pg 里面拉，我觉得得做
实时投影，这样实用性广，开源的时候不用别人装 pg」。所以 §5.50 选**投影**，而且放在**宿主侧**：
Lead 会话的事件日志就是权威来源，宿主侧手里有**全份**，与浏览器窗口无关，也不需要任何外部数据库。

- **折叠是纯函数**（新文件 `lib/team-log.js`）：`createTeamLog()` / `applyTeamEvent(log, event)` /
  `applyTeamEvents(log, events)` / `serializeTeamLog(log)`。只认团队运行时 append 的四种事件
  `team/member` / `team/task` / `team/message/queued` / `team/message/delivered`：
  member/task 是**整值记录**（同 id 后者胜），`queued` 是**只增的正文**（同 id 重放只留一行、
  seq/time 取最新——fork 回放不会多出一个气泡），`delivered` 只带 id，所以送达是**第二遍**。
  日志里没有的事件不会凭空出现：一条 queued 没有对应的 delivered，就是「排队中」。
- **读日志的门**（`lib/host/roster.js`）：`/team-log` 的处理函数够不着 `agents`，所以跟 §5.45 的
  `teamSend` 同一套路——在 `ctx.inject(['agents','agentTeams'], …)` 里往模块级 `teamLogReader`
  塞一个闭包。它按 `sessionId` 取 `agents.get(sessionId)` 的 live agent，再用
  `session.snapshotEvents(entry.scanned)` 只折**新增的那一段**（游标 = 已折的条数，`session.seq` 是
  日志长度）；日志变短（fork / 折叠重放）时游标超界，缓存**重建**而不是继续吐旧名册；
  `agent/disposed` 时把这个会话的缓存删掉。
- **端点**（HTTP 接口的完整清单属内部设计文档，未随本仓发布；端点本身在 `lib/host/routes.js`）：`200` 给投影，其余三种失败都是可回退的普通答案。
- **客户端**（`lib/client.js`）：`useTeamProjection(sessionId)` 每 4 秒轮询一次（页面
  `document.hidden` 时停），`mergeTeamLog(folded, projection)` 把投影与本地窗口**按 id 合并**而不是
  二选一——爆发时最新的事件只有本地有、最早的事件只有投影有；消息按可用的最大 `seq` 胜出，
  送达**任一侧看到就算送达**（一个迟到的轮询不会把「已送达」翻回「排队中」）。投影答上来了就
  `hasMore: false`（它从日志第一条折起，没有更早的可翻），并在表头显示「整份日志」；投影没答上来
  时 `mergeTeamLog` 原样返回 §5.48 的结果，一个字都不变。

`node --test`：**151 条**（§5.52 +1、§5.51 +2：见下一节。§5.50 那轮 +16：8 条纯函数折叠（`tests/teamLog.test.mjs`）、6 条 `/team-log`
端点（整份日志不被窗口截断、增量游标逐段折、日志变短就重建、409/405、没有运行时 503、disposed
清缓存）、1 条 §5.50 客户端源码断言（合并 + 轮询 + 回退）、1 条 §5.49 技能队列断言。
§5.48 之前那次的记录是 133 条，§5.49 的技能队列与 §5.50 的所有测试都在那一轮补上。）


### 事件驱动：任务板变化会唤醒 Lead（§5.44 / R4）

部署里**没有任何东西在看任务板**：`sendMessage` 全安装树只有一个调用点（`send_message` 工具自己，
`…\dsh-experimental-tool-agent-team\lib\index.js:312`），官方策略自认
`Task readiness never starts an owner`（同文件 `:27`）。所以「阻塞项完成了，新任务没人认领」这件事
本来只会静静地躺在板子上。插件补的就是这一段（`lib/team-watch.js`）：

- **在哪听**：挂在 **Lead 自己的 agent scope** 上（`scoped.on('session/event', …)`）——团队事件是
  **Lead 会话**的 append，`session/event` 只发给从该会话 emit ctx 收集到的观察者，
  挂在插件根上下文上永远收不到。
- **听什么**：`team/task` 事件只带 `{ version, teamId, task }`，里面**没有 `ready`、也没有动作**，
  所以收到事件后**回读 `listTasks()`**，只认两类**看得见的事实**：
  1. `status === 'pending' && ready === true && 没有 owner` —— 阻塞项刚完成，有活可做而没人在看；
  2. `status === 'in_progress' && owner 不在名册里` —— 活挂在已经离开团队的人身上。
- **怎么唤醒**：`agent.followup({ id, role: 'user', content: [{ type: 'text', text }], source })` ——
  inbox 目标是 `next-turn` + `wakeup: true`（`…\dsh-agent-loop\lib\index.js:806-811`），
  空闲的 Lead 立刻开一轮，忙的 Lead 在下一个 turn 边界看到。`source` 是机制自己的
  `{ kind: 'agent-team-roles', plugin: '@deepseek-ai/dsh-agent-team-roles' }`：这条提示**不是用户发的**，
  也不冒充某个成员；不投团队邮箱就不会顺带把成员唤醒。
  **`kind` 不能写 `'plugin'`**：那是 v3 的退役写法，v4 会直接拒收
  （`…\dsh-session-format-v3-to-v4\lib\index.js:126-128`），而且这条 append 一失败，
  该会话之后**所有** append（包括用户自己发的消息）都会报
  `format v4 message requires a producer-owned source kind`——整个会话就废了。
- **预算（自己带）**：`followup` 那条路**没有预算**（`wakeDriver()` 空闲就起一轮，`:854-875`），
  所以刹车放在这里 —— 同一个 `task.id:revision` 只提醒一次（去重键最多记 200 个），
  每个 Lead 会话**硬上限 8 条**（`NOTICE_MAX_PER_SESSION`）。自己唤醒自己的 turn 不是免费的。
- **不打扰正在干活的 Lead**：名册里 Lead 是 `running` 时直接跳过——它正在读自己的板子，
  这时再插一条通知只会让两个 turn 交错。
- **只提示、不自动指派**：插件不知道用户想把活交给谁，能做的是把「哪些任务可以开始」「谁的活挂了」
  连同 `team_task_update` / `send_message` 的用法一起说给 Lead，由它决定。

#### 第三类事实：成员空闲（`agent/status` 那一路，2026-09-28 补）

团队事件只有四种（`team/member`、`team/message/queued`、`team/message/delivered`、`team/task`），
**没有「某成员变空闲了」这一种**：成员可用性是**读时算出来的** ——
`availability(agent)` = `agent?.status === 'running' ? 'running' : 'inactive'`
（`…\dsh-experimental-agent-team\lib\index.js:727-730`，`memberView()` `:687-701` 把它拼进每行的 `status`）。
所以「谁空着」只能在 **agent 事件那条 lane** 上听：

- `…\dsh-agent-loop\lib\index.js:790-799`：`get status()` 把 `phase.kind === 'idle' | 'maintenance'` 读成 `idle`，
  `setPhase(next)` **先 `this.phase = next`、再**在状态真的变了时 `this.dispatch.emit('agent/status', { status })`
  ⇒ 我们的监听器跑的时候，成员**已经是** `idle`（回读名册拿到 `status: 'inactive'` 是准的）。
- payload 里的 `agent` 是机制注入的，不是各调用点自己带的：`agentEvents(ctx, agent, carrier)`
  把每个 payload 过一遍 `const fused = (payload) => ({ ...payload, agent })`（`…\dsh-agent\lib\types\dispatch.js:37-42`），
  所以 `agent/status` 的监听者拿到的是 `{ agent, status }`。团队运行时自己就在这条 lane 上
  （`…\dsh-experimental-agent-team\lib\index.js:1726-1729`、`…\dsh-goal-round-driver\lib\index.js:213-222`）。
- 插件侧用**同一个** `scoped`（`ctx.inject(['agents','agentTeams'], …)` 的作用域）注册
  `statusScope.on('agent/status', …)`（`lib\host\roster.js:135` 把 `statusScope: scoped` 交给 watcher）。
  **只认成员**：`status !== 'idle'` 直接返回；`teams.tryMembership(subject)` 答不出成员
  （普通子代理、陈旧身份 ⇒ `undefined`）或答的是 `role === 'lead'` 也返回 ——
  Lead 自己每轮结束都会 `running → idle`，不过滤就等于自己叫醒自己。
- **只在有活等人时才算数**：`idleMembers(members, tasks)`（`lib/team-watch.js`）先看
  `readyUnclaimed(tasks)`，**空就返回 `[]`** —— 成员大部分时间都 idle，单独一个 idle 不值得开一轮。
  非空时列出 `role !== 'lead' && status === 'inactive'` 且名字非空的行。
- 提示的第三段：「下面这些成员现在空闲（不在跑），上面那些没人认领的活可以直接派给他们：」+ `- 名字（模型）`。
  去重键在原 `task.id:revision` 之外追加 `idle:${名字,名字}` —— 成员跑完一轮正是要产生一条新提示的那一下，
  同一批空闲集合只提示一次；预算仍是每个 Lead 会话 8 条。

> ⚠️ 这一节（名册、角色名单、任务板监听、`team-send`）全在**宿主侧**
> （`lib/team-roster.js` / `lib/team-watch.js` / `lib/host/roster.js` 的 `agent/created` 与 `team-send`），
> 代码改动要**重启一次 dsh** 才生效；客户端那半（`@` 源）刷新页面即可。
