# 开源发布总流程

把一个内部插件变成「别人能一条命令装上、能用、能找到」的开源插件，全流程八步。
本文件只写**流程和关键注意项**；数据与依据见 [发布流程调研](发布流程调研.md)，体检结果见 [标准化清单](标准化清单.md)。

## 全流程一览

```
① 仓库标准化  →  ② 安装便利性  →  ③ 本地自测  →  ④ 初始化 git + 首次推送
     ↓
⑤ 打 tag / 发 npm（可选）→  ⑥ 提市场 PR  →  ⑦ 等合并  →  ⑧ 维护（版本/CHANGELOG/CI）
```

前四步不做完，后面全白搭：市场 CI 会直接读你的 `package.json` 与仓库年龄。

## ① 仓库标准化

**清单**（缺一条都可能被判不合格）：

- `package.json`：`private` 必须去掉；`license` / `repository` / `bugs` / `homepage` / `author` / `keywords`（必含 `dsh-plugin`）；
  `files` 白名单；`publishConfig.access: public`；`engines.node` + `engines.dsh` 双范围；`prepack` / `prepublishOnly`。
- `dsh.bundle.patch` **必须有** —— 这是「能被 `dsh plugin add` 安装」的唯一开关，只声明 `dsh.client` 市场 CI 直接失败。
- `cordis.patch.yml` 的 `insert[].name` 写**包名自己**，不要写相对路径。
- 根目录：`LICENSE`、`.gitignore`、`CHANGELOG.md`、`README.md`。
- README 里**不准留**作者本机绝对路径（`C:/Users/xxx/...`）和仓库外相对链接（`../../Docs/...`）；开源后这些全是死链。
- 快照/夹具里也别留本机绝对路径：要么存相对 `<DSH_HOME>` 的路径，要么在发布前清掉。

**本项目的取舍**（记录在案，别反复推翻）：

- LICENSE 用 **MIT**（不改），参考插件用 Apache-2.0，两者市场都收。
- **不加 `peerDependencies`**：本插件运行时不 import 任何 `@deepseek-ai/*`（只走 `ctx` 服务），
  而 dsh 的安装器会把「不满足的 DSH peer 依赖」当成**拒绝安装**的理由；`engines.dsh >=0.2.0-rc.1 <0.3.0-0` 已经够表达兼容性。
- `files` 带 `src` / `tools` / `docs`：便于审计，体积可接受。

## ② 安装便利性（最容易翻车的一环）

**标准安装就是一条命令**：

```powershell
dsh plugin --profile web add <spec>
```

- `<spec>` 三种写法：npm 包名 / `github:owner/repo` / `.tgz` URL，市场全收。
- 这条命令把参数转给 profile 目录的 pnpm，**成功后自动 reconcile `dsh.profile.bundles`**
  —— 用户**不需要**手工编辑 profile 的 `package.json`。凡是教你手改两处的 README 都是本机自用流程，开源版必须换掉。
- 装完必须**重启 dsh**：宿主半只在新进程里存在，热加载只覆盖客户端半。

**git 安装的坑**：pnpm 默认阻止安装期构建脚本。用户会看到报错并要求在
`<DSH_HOME>/profiles/<profile>/pnpm-workspace.yaml` 写 `allowBuilds`。发 npm 或发 tarball 可以完全绕开这一步。

**自检**：拿一个干净 profile 真装一遍，别在作者机器上「应该能行」。

## ③ 本地自测

- `npm test` 必须**在别人机器上也能全绿**：凡是依赖作者本机 profile / 绝对路径的检查，
  要么显式 SKIP（可见的跳过，不是静默通过），要么移出默认 test 脚本。
- 循环等待、无限重试这类漏洞测试要覆盖到；测试脚本进 git，测试截图/日志不进。
- `npm pack --dry-run --json` 自查包里到底装了什么。

## ④ 初始化 git + 首次推送

```powershell
git init -b main
git add -A && git commit -m "feat: initial open-source release"
git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main
```

**注意项**：

- 提交身份：agent shell 的 `GIT_CONFIG_GLOBAL` 被接管，读不到 `~/.gitconfig` → 用
  `git -c user.name=... -c user.email=... commit`，或在仓库里 `git config --local` 设一次。
- 提交前看仓库大小：单次增量超 5M 不正常（`lib/client.js` 是构建产物但**该提交**，别 .gitignore 掉）。
- 别把 `node_modules/`、`logs/`、测试截图提交上去。
- 想清空后重来：`git rm -r --cached .` 再重新 add，别 `rm -rf .git`。

## ⑤ 打 tag / 发 npm（可选但建议）

- 发 npm → 进官方「发现」索引（只收 npm 包）、用户装起来最快、免 `allowBuilds`。
- 不发 npm → 只能靠 awesome 列表 + `github:` 安装，官方发现页看不到。
- 发 npm 前：`private` 已去掉、`publishConfig.access` 写好、`prepublishOnly` 能跑通、包名没被占。
- 参考插件用 `v*` tag + OIDC trusted publishing，tag 必须等于 `v<version>`。

## ⑥ 提市场 PR

- 入口：<https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/pulls>
- 方式：**新增一个文件** `data/plugins/<owner>__<repo>.yml`（不是表单、不是 CLI）。
- yml 必填：`url`（与仓库完全一致）、`name: owner/repo`、`category`、`description.en`；
  含 `: ` 的描述必须加引号，否则 YAML 解析失败。
- 硬性前置：仓库**创建满 1 天**、仓库加 `dsh-plugin` topic、`package.json` 里有 `dsh.bundle`。
- 一个 PR 最多 3 条；分类 23 选 1，本项目建议 `workflow`。
- 合并后网站自动重建，不用再操作。

## ⑦ 等合并 & ⑧ 维护

- 合并后确认列表里 `install` 行正确、图标/截图正常。
- 之后每次发版：改 `version` → 补 `CHANGELOG.md` → 打 tag → （发 npm）→ 市场按包名自动更新版本。
- `dsh` 升到下一个次版本时，`engines.dsh` 的区间要跟着改，否则用户装不上。

## 一句话记牢的三条

1. **`dsh.bundle.patch` 决定能不能装，`dsh plugin add` 自动补 bundles，用户只需一条命令 + 重启。**
2. **作者本机的绝对路径和仓库外链接，开源前必须全部清干净。**
3. **市场 PR 是加一个 yml 文件，仓库满 1 天 + `dsh-plugin` topic 是硬门槛。**
